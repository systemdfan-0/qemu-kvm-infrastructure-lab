# Политика SSH-аутентификации и её проверка

[Главная](../../README.ru.md) · [English](../en/ssh-hardening.md) | **Русский**

Итоговая проверка доказала доступность SSH-баннеров, но не безопасность аутентификации ([проверки](validation.md)). Здесь описаны политика, чек-лист и инструменты, закрывающие этот пробел. **Статус:** политика и инструменты проверены только на временных локальных экземплярах `sshd`; на шести гостях лаборатории они ещё не применялись и не запускались.

## Политика

| Мера | Настройка | Причина |
|---|---|---|
| Вход по паролю | `PasswordAuthentication no`, `KbdInteractiveAuthentication no` | Убирает онлайн-подбор паролей |
| Методы | `AuthenticationMethods publickey` | Один явный метод |
| Root | `PermitRootLogin no` | Администрирование через именованную учётную запись и `sudo` |
| Учётные записи | `AllowUsers <административная запись>` | Служебные записи не могут входить |
| Подбор | `MaxAuthTries 3`, `LoginGraceTime 30`, `MaxStartups 10:30:60`, fail2ban (5 неудач за 10 мин → бан на 1 ч, nftables) | Замедляет сканеры; сеть управления не банится |
| Поверхность | `X11Forwarding no`, `AllowAgentForwarding no`, `AllowTcpForwarding no`, `PermitTunnel no` | В лаборатории не нужны; включайте на конкретном узле, если нужен jump host |
| Простаивающие сессии | `ClientAliveInterval 300`, `ClientAliveCountMax 2` | Закрывает «мёртвые» сессии |
| Доступность | Маршрутизатор `edge_input_mode: strict` | SSH только из сети управления и LAN, с ограничением частоты, INPUT по умолчанию DROP |

Настройки лежат в `/etc/ssh/sshd_config.d/00-lab-hardening.conf`. Префикс `00-` важен: `sshd` берёт **первое** прочитанное значение, поэтому более поздний drop-in (например `50-cloud-init.conf` с `PasswordAuthentication yes`) его не перекроет. Затем роль проверяет **действующую** конфигурацию по `sshd -T`, так что переопределение обнаруживается, а не предполагается отсутствующим.

## Применение

```bash
cd infra/ansible
ansible-playbook playbooks/ssh_hardening.yml      # также входит в site.yml
```

Защита от блокировки: роль останавливается, если у разрешённой учётной записи нет `authorized_keys`, проверяет файл через `sshd -t` до установки и только перечитывает (не перезапускает) демон, поэтому открытые сессии сохраняются. Держите вторую сессию открытой, если применяете политику на машине, к которой нет физического доступа.

## Чек-лист проверки

1. `ansible-playbook playbooks/audit_ssh.yml` – каждая строка политики даёт PASS по *действующей* конфигурации; `ssh` и `fail2ban` запущены.
2. С клиента: `python3 scripts/ssh_check.py --user debian --identity ~/.ssh/id_ed25519 192.168.150.11 192.168.150.12 …`
   - баннер получен;
   - объявляется только `publickey` (без `password` и `keyboard-interactive`);
   - вход root с валидным ключом отклонён;
   - обычный вход по ключу работает (положительный контроль, чтобы отрицательные результаты что-то значили).
3. Проверка бана: с одноразового клиента сделайте больше `f2b_maxretry` неудачных попыток и проверьте `fail2ban-client status sshd`. Не делайте этого с управляющей машины Ansible: её сеть в списке исключений.
4. Доступность маршрутизатора (режим strict): проверка 11 в `verify.yml` теперь должна показывать *закрыто* из DMZ.
5. Заносите даты и результаты в [проверки](validation.md) только после запуска на настоящей лаборатории.

`scripts/ssh_check.py` не отправляет пароль: `ssh` запускается в `BatchMode`, где запрос пароля невозможен. Host key при пробах не проверяется, так как пробы не передают секретов; для настоящих входов используйте свой `known_hosts`.

## Что реально проверено

- `sshd -t` принимает сгенерированный drop-in.
- Строки проверок совпадают с реальным выводом `sshd -T`. Это нашло ошибку: современный OpenSSH печатает ключи в CamelCase, старые версии — в нижнем регистре, поэтому сравнение регистронезависимо.
- На усиленном локальном `sshd` проба показала только `publickey` и успешный вход по ключу; на намеренно слабом — `FAIL`, так как объявлялись `password` и `keyboard-interactive`. Проверка root осмысленна только на демоне, способном пускать root, поэтому здесь она не выполнялась.

## Не охвачено

Жизненный цикл и отзыв ключей, аппаратные ключи или SSH-сертификаты, многофакторная аутентификация, bastion-узлы, пересылка логов и оповещения, закрепление host key. Это разумные следующие шаги; они не заявляются.
